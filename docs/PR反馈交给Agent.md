# PR 反馈交给 Agent

## 做什么

工作台的「收件箱」（`#/inbox`，原「消息」页和更早的「PR 待处理」`#/prs` 都并进了这里）列出你开着的全部 PR（「我发的 PR」里全有），按谁最后说话分进「待你回」「Agent 处理中」，在等对方的只在「我发的 PR」里。「待你回」里有两种交给（用户 2026-11-18 要求）：勾选多条点「帮我回复（勾选 N 条）」或「处理并回复（勾选 N 条）」，或点「全部帮我回复（N 条）」「全部处理并回复（N 条）」（点开一条 PR 的详情也有这两个按钮并列），Agent 逐条处理。回复 Agent 不发：它把要发的回复写成草稿，这一行进「草稿待确认」，你看过、改过、点「确认发送」才用你的账号发出（见下面「回复草稿」）。

- 帮我回复：只回复。Agent 读全评论、评审和必要的代码，只把回复写成草稿；不改代码、不建工作区、不推送、不开或关 PR、不转草稿。对方要改代码的，草稿里如实写要怎么改，回执里提示改用「处理并回复」。适合对方只是问问题、确认口径、要个说法。
- 处理并回复：下面的完整流程。

每行状态那句话后面标一个建议：对方最后几条（你最后一次动作之后的；没有就看对方最后一句）在提问、确认口径、让你选 1A 1B 的标「只需回复」；评审要求修改、带代码建议或修改意见的行内评论、要求改代码、补功能、修 bug 的标「需要处理」；判不准标「只需回复」。只用已经读到的时间线，不另发请求；鼠标停在上面看依据。建议只是提示，两个按钮都能点。

模式（`mode`：`reply` 帮我回复、`handle` 处理并回复）由 `POST /api/prs/handoff`、`/api/issues/handoff` 带上，写进交给记录；监看把它作为 `prs.feedback` 事件派出时，detail 第一行写「模式：只回复（…）」或「模式：处理并回复（…）」，技能照它走。没写模式的旧记录 detail 里没有这一行，按处理并回复。草稿「重新生成」照上一次的模式再交。

处理并回复时：

- 对方要你改：从远端的 PR 头开一个游离工作区（不碰本地任何分支），按意见改、跑项目已有的检查、提交、推回 PR 原分支，再把给评审人的逐条回复写成草稿（行内意见的回复对准那条线程，写怎么改的和提交号）。
- 对方只问了问题：回答写成草稿，不改代码。
- 对方让转草稿之类只做动作的：做完，写一句回复草稿。
- 对方让关闭：关闭 PR，礼貌回复一句写成草稿。
- 对方让换方向：按新方向在原分支上重做。
- 对方说不用改、他们来改、先不收、保持草稿，或你已经照做了：不改代码，也不写回复草稿，只在汇报里写对方原话的要点。

Agent 不合并 PR，不新开 PR，不强推（对方明确要求 rebase 或 squash、只能强推时用 `--force-with-lease`，并在回复里说明）。提交、回复和 PR 文字里不提任何 AI 工具。

## 怎么判断「对方回了、你还没回」

看 PR 时间线，比较两个时间：

- 你最后一次动作：你的主楼评论、评审、行内评审回复、提交、转草稿或转可审。在别处引用这个 PR 不算回应。
- 对方最后一句：别人留的主楼评论、行内意见、带文字的评审或要求修改。行内意见按发布时间算：评审人先起草、后随评审提交的，算提交那一刻。只点「批准」不写字的不算。非维护者用邮件发的评论不算（订阅者邮箱的自动回复，如“邮件已收到”“假期自动回复”；维护者用邮件回的照常算）。机器人不算（GraphQL 里是 Bot、login 以 `[bot]` 结尾，或 coderabbitai、codecov、github-actions、vercel、claude 等自动评审账号）。

对方最后一句晚于你最后一次动作，就列进「待处理」。

每条回复都标身份。仓库主人（OWNER）、组织成员（MEMBER）、协作者（COLLABORATOR）和被请求评审的人算维护者；其他人（贡献者、路人等）照样列出，标「非维护者」。Agent 只照维护者的要求改代码、rebase 或强推、换方向、关闭 PR；非维护者的话最多回答问题，要求改动的写成卡住，等你决定。

交给 Agent 时记下当时对方最后一句的时间。这一轮处理完（推送、关闭、回复或不用动）后，对方没有更晚的回复，这条就收进下面折叠的「最近处理过」（保留 7 天）；对方又回了，它回到「待处理」，可以再交。等你决定、等你看、已交给的，你自己在那之后动过手、对方没有新回复，也收进去。回执说推送或回复了、时间线里却没有你账号在这一轮之后的动作的，降为等你看。

## 页面上看到什么

每行一条 PR：仓库和编号、标题、项目、评审结论、草稿、几条新回复、谁说了什么（最多 5 条，点了去 GitHub 原处）、你最后一次动作的时间、处理阶段。

阶段：未交给 Agent → 已交给 Agent → 处理中 → 已处理 / 等你决定 / 等你看。

- 已处理：结果写「已推送 abc1234」（点了看提交）、「已关闭」「已回复」或「不用动：原因」。
- 等你决定：Agent 卡住了（写原因），或问了你一个问题（在这一行直接回答）。
- 等你看：回执没有结果行、读不到或这一轮没跑完。

已交给、还在派或在处理的不能再勾；两个请求同时交同一条，也只记一次。中台还没装「处理 PR 反馈」规则时，交给会直接报错，提示先运行 install。交出后超过 15 分钟还没有新的一轮，标「派发可能丢了」，可以再交。刚交给的每 10 秒刷新进度。

## 回复草稿

Agent 把回复存进本机 `.personal/reply-drafts.json`（技能里运行 `scripts/reply_draft.py save <草稿.json>`，这个脚本不发评论），按 `owner/repo#编号` 一条，记生成时间和生成时对方最后一条评论。草稿里每条回复写回复给谁和正文；PR 行内意见的回复带那条线程首条评审意见的 id，旁边写 Agent 做了的代码改动和推送。回复里出现 AI 工具的名字或署名行，保存和发送都会被拒。

- 收件箱「草稿待确认」（在「要你处理」一组，计入角标）列出有草稿的行；点开详情看草稿全文，可以直接改，按钮「确认发送」「重新生成」「丢弃」。
- 确认发送：工作台先重读一次这条 PR 的主楼评论、行内意见和评审，对方在草稿生成后又说了话，就提示「对方又回了 N 条，草稿可能过时」并列出最近几条，你选「仍发送」或「重新生成」。然后用你的账号逐条发：普通评论用 `gh pr comment`，行内回复用 `POST repos/<owner>/<repo>/pulls/<编号>/comments/<id>/replies`。全部发出后删草稿，这一行回到等对方；某条发送失败，写中文原因（没登录、没有权限、找不到、评审意见已不能回复、连不上 GitHub……），已发出的从草稿里去掉，其余留着可以再发。
- 重新生成：照原流程再交给 Agent，交出去了才删旧草稿。
- 丢弃：删草稿，不发出去；Agent 做了的代码改动和推送不受影响。
- 列表上勾选多条点「确认发送（勾选 N 条）」或「全部确认发送（N 条）」，先在页面里确认一次，再逐条发、逐条写结果（已发出、对方又回了没发、发送失败的原因）。

回执说回复了、时间线里还没有你的评论时：这一轮写了草稿（或草稿已发出、丢弃、重新生成）不算「等你看」；没找到草稿才标「等你看」。

## 怎么接到中台

页面不写 GitHub，也不在别人的仓库打标签（没有权限）。交给时工作台把 PR 记进 `~/.agent-autoloop/issues/pr-handoffs.json`，马上触发一次监看；监看把一天内交给的 PR 作为 `prs.feedback` 事件交给中台，规则「处理 PR 反馈」用技能 handle-pr-feedback（正本在 `personal/skills/handle-pr-feedback/SKILL.md`）处理。中台没接上时，工作台的监看闸门 10 分钟内再触发一次。

第一次用之前运行一次：

```sh
cd /Volumes/Luochen/工作/开源/workbench   # 仓库根目录
python3 -m personal.agent_watch install
```

它链好技能、在 `~/.agent-autoloop/rules.json` 里加上事件和规则（原文件先备份）。中台会自己读到新规则；没生效就运行 `launchctl kickstart -k gui/$(id -u)/agent-autoloop`。

## 授权

交给 Agent 后，Agent 在你自己开的 PR 上推送、按维护者意见关闭 PR，是你 2026-11-13 授权的。回复不由 Agent 发：2026-11-18 起改成先草稿后确认，页面上「确认发送」是工作台对 GitHub 的写操作，只发你审阅过的草稿。
