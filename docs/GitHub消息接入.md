# GitHub 消息接入

## 当前行为

GitHub 通知并进收件箱（全部），项目详情里的「GitHub 消息」只列这个项目的。使用当前 gh 登录身份，只读同步已读和未读通知；可按未读、仓库、类型和标题筛选。通知和同一条 issue、PR 的处理情况合成一行，提供 GitHub 原文入口。

归类顺序：当前项目的仓库精确匹配 → 当前项目的旧名称/协作别名 → 多义匹配待核对 → 已登记但没有近期本人提交的暂缓项目 → 其他仓库。匹配只使用可信仓库配置，不通过通知标题猜归属。消息不能自动激活项目或派发执行。

点击消息只读最新回复，缺少回复时读主题正文。CI 等类型没有可用正文时提示看 GitHub 原文；失败保留通知摘要，不伪造正文。页面按纯文本展示外部内容。

## 本机保存

每次同步把结果写进数据目录的 `github-notifications.json`（临时文件再改名，写一半不会留下坏文件）：

| 字段 | 用途 |
|---|---|
| account | 同步时的 GitHub 账号 |
| synced_at | 同步时刻；页面超过 5 分钟才再同步 |
| ids | 本次同步里的通知线程编号，页面只列这些 |
| rows | 线程编号 → 通知原文（仓库、原因、未读、更新时间、主题标题和地址、上次读的时间） |

归类结果每次读页面时按当前 `projects.toml` 重新算，不存。重复同步只覆盖这一份文件，不建任务。正文仅按需读取，不写进离线快照或源码。

旧版把通知存在本机任务库 `tasks.sqlite3` 的 `intake_records` 表里。第一次读到没有 `rows` 的同步结果时，从那张表只读导入同一账号的通知原文并写回 `github-notifications.json`，之后不再读任务库；任务库本身不改。

## 已核对的真实结果

2026-11-06 首次完整同步读取 306 条真实通知，101 条未读；按当时提交范围归类为当前工作台 191 条、暂缓项目 79 条、其他仓库 36 条。读取了一条真实最新回复，正文 1,433 字符，无读取错误。

这些是本次同步时的结果，后续随 GitHub 通知变化。首批未分页结果为 50 条，完整实现会继续分页，不把首批数量当作总数。

## 验证边界

离线测试覆盖精确仓库匹配、旧名称、暂缓项目、多义映射、标题不能改变归属、GET 限定、分页、正文资源主机和仓库边界、同步结果的本机保存和旧任务库的一次性只读导入、读取失败保留上次结果，以及没有自动建任务。

GitHub 标记已读、回复（「确认发送」回复草稿除外，见 README）、关闭 Issue、合并或自动执行均未接入。用户主动打开 GitHub 原文后的行为由原站处理。
